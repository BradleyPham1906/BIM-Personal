## Alternatives — compare, do not prematurely select

1. **Use upstream modules unchanged behind an adapter.** Best aligned with reuse-first if the relevant API, legal boundaries, WASM isolation, size, offline delivery and failure semantics can be shown to work. Concrete observations: `solidcraft-doc` has substantial dependencies and the current web target is a complete app. These are integration questions, **not a demonstrated blocker**.
2. **Extend current JS mechanisms.** Avoids a new runtime but risks recreating tested functionality. Existing sketch solver, mesh operations and graph are starting points, not proof of the required feature-history slice. Document each gap and why upstream reuse is unsuitable before implementing replacement logic.
3. **Port a bounded algorithm.** Only when direct reuse has a verified incompatibility and a port is justified; preserve attribution, tests and semantic equivalence. Rust alone is not an incompatibility. No such blocker has yet been verified.

The recommendation **at this point** is to complete the source/counterpart audit and request approval for an isolated unchanged-upstream test. No kernel, build-system change, port, schedule or delivery promise has been selected.

## Acceptance oracle and proof-of-concept plan — not executed

For the specified 4 m × 3 m rectangle and 0.3 m Pad, independent rectangular-prism arithmetic gives 3.6 m³; changing width to 5 m gives 4.5 m³. If a fully contained, non-through 1 m × 1 m × 0.1 m pocket is explicitly placed and cut, ideal volumes become 3.5 and 4.4 m³ respectively. These are hand-calculated expectations **only under the stated placement and no-overlap assumptions**; not results from either app or a geometry kernel. Define sketch and pocket coordinate frames, orientation, tolerances, expected topology and reference identity before execution.

After owner approval, isolate the pinned upstream with no production data/tokens; document exact build dependencies and commands. First run unchanged upstream, then test a minimal adapter: create the sketch, pad and contained pocket; change the dimension, rebuild, return mesh and feature records, and save/reopen inputs. Verify against independently calculated bounds and volume, not screenshots alone. Measure actual payload and initialization on supported devices and prove intended offline/file:// behavior. Compare with the existing JS path using the same fixtures. Do not build or execute third-party code merely because this document describes it.
