## Abstract
How can the existing model show convincing pond and flood-water presentation without changing analysis results, losing the ability to fall back, or implying the animation is a validated flood solver? Recommend an incremental, explicitly non-authoritative presentation layer driven by immutable, revision-matched analysis snapshots: first a clipped static pond surface in the existing rendered-view path, then optional small-amplitude visual ripples and a single limited planar reflection; defer caustics and refraction until measured. The current V143 result supplies a sampled terrain grid, fill surface, mask and flow summary, not a dynamic 3D hydraulic model. Source inspection found an important identity hazard: pond IDs are assigned in discovery order but the pond summary list is sorted by volume; do not index the sorted list by `pid - 1`. This is a source-derived integration risk, not a proven current user-facing bug. A local synthetic fixture demonstrates the mismatch but does not execute the app.

## Findings
### Existing data and integration (P, high for selected functions)
`analysis/simulation.js` [1] samples the TIN into a grid, fills depressions with Priority-Flood, computes D8 flow/accumulation and connected cells above `pondMin`; each pool summary has area, volume, maximum depth, level and low point. The returned `ok`, `H`, `F`, `pid`, grid origin/cell size, and `stamp` give *potential* presentation inputs; the plan overlay currently colors any nonzero `pid` and draws flow only in plan view. They are not proof of a meshed pond or flood hydraulics. `F` includes an epsilon gradient in the fill; using it blindly as a physically level water surface would introduce slope. Any proposed constant level, mask and shoreline must be verified against original elevation and local spill relationships; the group `level` is the maximum sampled filled elevation, not automatically a hydrologically approved water level.

The function assigns `pid` values while discovering connected components, then sorts `ponds` by volume before returning. A consumer can use nonzero `pid` as a mask, as the current plan display does, but **must not assume `ponds[pid-1]` is that component** after sorting. Extend the result with an explicit immutable ID in each pool, or build a discovery-order lookup *before* sorting, and test with two differently sized pools. Preserve or adapt other consumers rather than silently changing an existing public contract. Confirm actual downstream assumptions by code and integration tests before calling this an application defect.

`rendered-scene.js` [2] builds a scene from shared chunks plus terrain, keeps camera/visibility and uses site sun. `rendered-view.js` [3] owns a separate three.js rendered view, cached scene signatures, accumulation passes and context-loss/shaded fallback. Visual water animation affects the accumulated-frame signature and scheduling: without explicit invalidation or a dynamic pass, old frames can ghost or refinement can continually restart. Presentation and sheets are explicitly reported as 2D in this path; do not promise 3D water in them without separate integration work. The actual surface is not yet proven to appear in save/export, picking, section clipping or saved views.

### What the reference demo does (P, high for source; scope-specific)
The demo stores height, vertical velocity and two normal components in floating-point textures; `water.js` uses two textures and swaps them, samples four neighbors, damps and updates, then computes normals [4]. Its fixed values and texture size are demo choices, not engineering parameters or evidence of stability on all inputs/devices. `renderer.js` computes rays against a sphere and a box with sky fallback, uses separate above- and below-water cases, and renders a caustic texture; it explicitly requests derivatives or substitutes a constant value [5]. It is not general scene ray tracing or general flood simulation. Its file headers identify MIT; no third-party assets are authorized by that header alone.

Wallace's explanation [6] maps a refracted light wavefront mesh onto a receiver and approximates the change in light concentration from the original/new area ratio. It is effective for its simplifying assumptions, not a global-illumination solution. Near a degenerate projected triangle the ratio grows very large; implementation must guard, bound and test denominators while admitting the bound is artistic, not validated energy conservation.

### Alternatives and counterexamples (P, medium for transfer to BIM)
NVIDIA's practitioner chapter separates geometric waves from a finer normal map and describes mesh/texture sampling, shoreline attenuation and aliasing tradeoffs [7]. It does not validate drainage physics. Its separate caustics chapter explicitly says its real-time method is a physical simplification; screen-space and texture-space approaches trade visible-pixel work against fixed-target work and aliasing [8]. The SSR prototype's author documents missing reflections from off-screen or occluded surfaces [9]; environment maps likewise lack nearby dynamic scene detail. A planar reflection can show reflected geometry but needs an additional scene render, clipping and measured integration effort. No approach here establishes performance for this app.

Khronos `EXT_color_buffer_float` [10] applies to WebGL 2 and makes specified float formats color-renderable when the extension is provided; texture sampling, linear filtering, multisample support, framebuffer completeness and device memory are distinct concerns and should be checked separately. Never infer all capabilities from a single extension flag. WebGPU's device limits and lifetime require a separate backend audit; the earlier WebGPU note is not a completed implementation.

## Alternatives compared
Criteria: preserve authoritative analytical data and 2D workflows; visible quality; bounded cost and compatibility; testability; only then integration complexity. None has been benchmarked on this app.

| Approach | Use | Benefits | Risks and boundaries |
| --- | --- | --- | --- |
| Existing plan mask and flow | Baseline | Already visible in the inspected plan code | No reflective 3D water; not time-varying hydraulic output |
| Flat masked 3D surface | First proposed vertical slice | Stable, inspectable; no animated GPU state | Shoreline contouring, holes, ID mapping, z-fighting and stale results require testing |
| Analytic normal-map ripples | Optional visual enhancement | Cheap candidate, no solver state; can freeze for export | Visual only; aliasing and repeating patterns; performance is unmeasured |
| Heightfield ping-pong ripples | Interactive graphics prototype | Local impacts and animated surface | Requires renderable/filterable targets, stability and memory tests; one height per location cannot represent overhangs or breaking waves |
| Planar reflection plus fallback environment | Optional second pass | Captures reflected local scene for a plane | Additional render, clipping and edge behavior; one plane not arbitrary curved surface |
| Screen-space reflection | Later experiment | Uses visible screen data | Missing off-screen/occluded information, edge artifacts [9] |
| Caustic texture projection | Later opt-in | Suggestive refracted light under controlled receiver assumptions | Degenerate concentration, receiver complexity, shadowing, moving sun, cost; not photometric proof |

## Proposed architecture and staged delivery
1. **Snapshot contract (proposal, U):** capture terrain/result stamp, grid origin and cell size, `ok`, `H`, filled elevations and connected membership; label source as static exploratory rain output with units, assumptions, source revision, no hydraulic certification. Reject hidden, missing, stale, superseded or invalid terrain. Keep source data immutable; no save/undo of temporary visual mesh.
2. **Explicit identity:** fix/extend mapping without relying on the sorted array position. Test multiple components, equal-volume ties, split/merge, missing cells, changes to pond threshold and sorting order; re-evaluate IDs on rerun. Recalculate neither survey nor saved pond metrics as a side effect of rendering.
3. **Geometry:** generate masked, clipped water patches from selected pool components; preserve holes and disjoint areas; establish which reference elevation defines each pool and reject contradictory/discontinuous inputs. Consider cells versus contour extraction: cells are simple but blocky; contouring needs interpolation and topology tests. Clip to shoreline, handle small holes, positive/negative elevation, depth and vertical datum; test thin cells and zero-area triangles. Avoid arbitrary z offsets that misrepresent elevation; measure depth bias/z-fighting and label any visual-only offset.
4. **Render integration:** prototype in the rendered-view scene path, with cleanup and revision keys, and fall back to existing shaded/plan representation. Check layer/level visibility, section cuts, camera projection, sun, draw order, transparency, antialiasing, Save image and 2D sheet boundaries. Avoid stale accumulation when water changes. Decide whether dynamic water freezes during still accumulation or runs in a separate compositing pass; prototype both before choosing.
5. **Visual embellishments:** choose authored small ripples or heightfield only after static geometry passes. Fixed-step update with bounded timestep and explicit domain boundary conditions; test flat state, impulse, stability over long playback and frames of different durations. Place plane/cubemap reflections first; add caustic projection only for supported receiver cases. A visual-only animation must never update drainage inputs, analysis outputs, schedules or design model.
6. **Performance and availability:** track cold start, warm median and tail frame time, memory, upload and GPU completion with one/multiple ponds at agreed viewport/quality on real desktop and mobile GPUs. Test no extension, failed framebuffer, context loss, memory allocation failure, tab suspension/resume and cleanup. Degrade in order: disable caustics/animated ripples/reflections, use a flat surface, then revert to current view. Avoid hard-coded universal thresholds until measured.

## Verification matrix and risks
- **Correctness:** analytical fixture with basin and spill elevation, steep terrain, irregular boundary, islands/holes, adjacent/overlapping groups, sorted IDs, small and large coordinates, missing/no-data, datum and units, stale revision and layer state. Compare generated mesh to known input; do not infer watershed correctness from appearance.
- **Rendering:** above/below water, grazing angles, off-screen reflectors, sky/no site location, occlusion, zero-area caustic projections, sun below horizon, transparent surfaces and section cuts. Reference images need explicit numerical/visual acceptance thresholds and independent review.
- **Lifecycle:** edit terrain while rendered, delete terrain, rerun analysis, undo/redo, switch tabs, hide layers, resize, export, context loss, low memory and fallback. Check no model mutation and no leaking GPU resources.
- **Reproducibility:** fixture above is narrow; no real scene, browser, devices or screenshots were checked. NVIDIA chapters are old practitioner sources and hardware statements are historical. The inspected code is a limited slice; all consumers of `pid`, current version of downstream paths, and other flood features remain U. Keep `Preparing`; research-completion rules require independent source review and resolving U before implementation.
