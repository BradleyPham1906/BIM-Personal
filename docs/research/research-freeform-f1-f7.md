# Freeform F1–F7: curves, surfaces, analysis and output — research draft

Research date: 2026-11-13. App baseline: 95b7aee4db8be1fc28c0fbe7befc7407fabd1dda. This is a phase-spanning research draft, not an approved specification, code implementation or completed research gate. The Parametric Design workstream belongs inside F1–F7 [1,2]. Prior SMLib research reported an independently checked build experiment; this draft did not repeat it [3]. Here, no upstream code or the app was executed. No independent reader checked this new report.

## Abstract

Question: how can F1–F7 support editable freeform modeling, surface evaluation and documented 2D/render output without mistaking a display mesh for its authoritative geometry or breaking the existing project? The evidence favors keeping native editable curves and surfaces, separate topology where needed, and revisioned disposable view tessellations, while extending existing app infrastructure and testing each integration boundary. Exact kernel choice, persistence format, advanced operation semantics and device budget are unresolved. A small independent Python calculation illustrates rational-curve weights and a cap in the current arc tessellation helper; neither calculation tests the app. The proposed acceptance cases below have not been executed in the application.

## Questions, falsifiable hypotheses and findings

| Hypothesis | Finding |
| --- | --- |
| A polygon mesh can fully substitute for editable NURBS and topology. | Not generally: OCCT distinguishes parametric geometry, topological boundaries and approximating triangles [4]. A faceted export can still be useful if labelled. P, high for the conceptual distinction; no app comparison. |
| A NURBS circle can generally use all unit weights without changing shape. | False for the specific standard rational quadratic quarter-circle fixture: 101 sampled unit-weight points deviate by up to 0.06066 radius; weighted sample radius error was 2.22e-16 in this Python run. P for this fixture, not proof of general algorithm [5,6]. |
| Zebra stripes by themselves certify G2 continuity. | Unsupported: Rhino presents Zebra as visual inspection [7]; numeric geometric continuity must be assessed against an agreed tolerance and correspondence. U for the app's eventual display and metric. |
| A requested chord tolerance is guaranteed by the inspected arc flattening helper. | False for its documented formula in at least one mathematical case: the 256 segment ceiling limits a 10 km-radius half-circle's resolution to 0.188 m sagitta rather than 0.002 m. Source-derived arithmetic only, not an observed user-visible defect or evidence this example occurs in the app [8,6]. |
| Existing dependency-graph behavior automatically satisfies strict feature-history failure handling. | Not established. In inspected source, cycles are reported but nodes are still visited in model order; visitor exceptions are counted and later nodes processed. A new feature system demanding cycle rejection/atomic rebuild cannot just assume identical semantics [9]. P for inspected source; integration untested. |
| Screenshots alone are enough for Make2D. | Not generally: visible and hidden line extraction needs explicit camera, occlusion and edge classification; OCCT separately documents shape-based and polyhedral hidden-line methods [10]. P for vendor's documented methods; actual target fidelity untested. |

## Seven-phase scope and investigation

| Phase | Source scope [2] | Input and output / research implication | Edge and acceptance evidence still needed |
| --- | --- | --- | --- |
| F1 | Degree 1–5 NURBS, interpolation, control editing, direction, rebuild, knot insertion and curvature graph | Persist degree, dimension, control points, weights, knot representation, parameter domain, periodic/closed flag, units and tolerance. Distinguish interpolating through points from control-point editing; rebuild is approximate unless demonstrably shape-preserving. Knot conventions differ: Rhino's guide notes its count differs from some textbook implementations [5]. | Rational circle, nonuniform/repeated knots, endpoints, degree bounds, reversed/periodic curves, coincident input, invalid/zero denominator; knot insertion shape unchanged to measured tolerance; interpolation residuals and clear failure on duplicates. |
| F2 | Extrude, revolve, rail revolve, loft, planar and edge surfaces | Construct native surfaces and retain input lineage; Rhino documents different loft styles and rail/profile/seam workflows [11]. Do not promise one unique result from mismatched profiles. Planar trims need loop/hole orientation and robust intersection. | Open/closed profiles; different degrees/knots, reversed order, shifted seams, self-intersection; exact cylinder/cone/sphere cases and failed nonplanar loop; loft section distances at specified parameter mapping. |
| F3 | Sweep 1/2, pipe, cap, join polysurfaces | Distinguish an open shell from closed, oriented, valid solid. Sweep requires frame transport/rail orientation decisions; a pipe around tight bends can self-intersect; cap requires suitable planar closed boundaries. Do not infer valid solid from visually sealed triangles. | Zero tangent, sharp kink, frame flip, nonplanar/multiple holes, small gaps, nonmanifold adjacency, self-intersection, inner/outer shell orientation; independent watertight/volume checks. |
| F4 | Zebra/environment, Gaussian and mean curvature, draft angle, naked/nonmanifold edges | Visual reflection and false-color inspection are diagnostic, not a numeric certificate [7]. Define normal orientation, pull direction, signed curvature convention, principal/Gaussian/mean values, units and color range; distinguish exact surface derivatives from mesh approximations. | Plane principal curvatures 0/0; cylinder has principal magnitudes 1/r and 0 (sign depends on chosen normal); sphere magnitudes 1/r each, Gaussian 1/r²; singularities/zero derivatives and seams shown unavailable rather than zero; compare against numeric reference. |
| F5 | Surface control points, blend curve/surface, match surface for G0/G1/G2 | Preserve original objects and editable history; G0 position, G1 tangent plane/direction, G2 curvature continuity are geometric concepts distinct from C1/C2 parameter-derivative continuity [4]. State correspondence, orientation, tolerance and behavior at ends. | Near-misses, reversed normals, degenerate tangents, curvature mismatch and reparameterized seams; independently sample distances, tangent angles, curvature across entire join, not one colored pixel. |
| F6 | Picture planes, scaled tracing, text outlines/solids, FlowAlongSrf | Store image provenance/rights and physical scale with attachment identity. Text needs font licensing, shaping, glyph contours, holes and units; topology of extruded glyphs is not guaranteed. Surface flow requires UV mapping/domain, distortion, seams and outside-domain policies. | Multiple image aspect ratios, scale bar and stale/missing asset; multilingual/RTL glyphs and holes, missing font; UV seam, trimmed areas, mirrored normals, severe distortion, no silent clipping. |
| F7 | Make2D (visible/hidden edges to sheet) and point/area/sun lights, rendered image | Freeze view, geometry revision, object/layer visibility, projection, scale and hidden-line method. OCCT documents geometric and polygonal HLR as different approaches [10]. Rendering requires color/lighting/display conventions and export provenance; a shaded image is not a line drawing. | Front/angled/occluded box, silhouettes/curves and coincident edges, transparent objects, perspective, clipping, layers and stale source; independent view-space expected coordinates and visible/hidden classification; compare pixel output only with defined engine/tolerance. |

F1/F2 are separable from solid-kernel adoption, but curves do not automatically guarantee correct trimming, topology, booleans or solids. The parent task records the previous recommendation to investigate verb-nurbs as an ES5 F1 candidate; actual selection is not approved [1,3]. F3/F5/F7 may need additional functionality and should not be scheduled by reusing the prior 112-hour estimate without decomposition.

## Alternatives and preliminary recommendation

Criteria fixed before comparison: editable fidelity and failure visibility, reuse of current app and delivery contract, validated operations, dependency/license cost, device performance, and round-trip interoperability.

| Option | Benefit | Limitation / decision |
| --- | --- | --- |
| ES5 NURBS library plus existing app objects | Potentially smallest initial curve/surface integration and consistent offline experience | Test actual pinned candidate, license, interpolation/derivative behavior, trimming and project persistence; library is not automatically a solid kernel. |
| Embedded WASM B-rep kernel | Exact analytic/topological operations may cover later needs | Prior SMLib e02 is useful limited evidence; open issue inputs, multi-browser/phone, reliability, worker lifecycle and distribution rights still need verified comparison. First binary dependency requires owner decision. |
| Mesh-only operations | Reuse existing rendering and previews | Approximate, topology and edit history weaker; cannot claim NURBS editability or exact analytic Make2D. May be opt-in visualization/export, with tolerance recorded. |
| Hybrid native geometry plus tessellation/optional solid kernel | Preserves edit source and creates render caches, allows staged decisions | Requires consistent versioning, source/cache invalidation, failure UX and precise interfaces; proposed approach, not already implemented. |

Recommendation: staged hybrid investigation with F1 mathematics and integration corpus first; treat a solid kernel as an explicit later decision, not a predetermined choice. Re-evaluate if tests show ES5 cannot satisfy measured accuracy/performance, build rules change, or independently reproduced solid-kernel failures rule out a candidate. Full F1–F7 feature implementation is not authorized by this report.

## Experiment and raw observations

Self-authored `fixtures/freeform-f1-f7-fixture.py`, one run `python3` 3.13.15 Linux, no dependencies or downloaded code. A rational quadratic uses control points (1,0), (1,1), (0,1) and weights (1, √½, 1). Across t=0…1 at steps 0.01, maximum absolute radius deviation was 2.220446049250313e-16; with all weights 1 it was 0.0606601717798212. Floating-point samples do not establish universal exactness, full NURBS evaluation, or production tolerance.

The inspected `bimArcSegments` [8] computes a chord-tolerance-based segment count then clamps it to 256. For radius 10,000 m, half-circle sweep π and tol 0.002 m, this independent calculation gives 2,484 required segments before the cap; 256 segments yield 0.188247173989 m sagitta. This falsifies a universal interpretation of the comment “max chord-to-arc departure”; no app render or downstream consumer was executed. The fixture models the inspected formula under ordinary positive values; it is not a precision audit or confirmation of a real project defect. Proposed follow-up: either explicitly report unmet tolerance when cap reached, permit a measured resource-bound adaptation, or reject the request; test affected consumers before deciding. Raw output: `fixtures/freeform-f1-f7-results.txt`.

## Current app: concrete text-only integration observations

- `drawing/arc-storage.js` [8] stores circular bulges alongside polyline points; `bimFlattenPoly` produces points and `bimArcSegments` caps at 256. The code comments state bulge cannot describe a spline or true ellipse. Do not treat this as a complete audit of all entity types, export consumers or live behavior.
- `io/project-file.js` [12] wraps `bimProjectRecord()` in `acad3d-project` format version 2 and warns for newer formats. Whether additional native geometry survives save, restore, undo, export, cloning and older app versions is untested. Respect existing object/project ownership and establish migration/unknown-field policy.
- `bim/dependency-graph.js` [9] derives edges from the live model, uses a dirty-subset topological sort, and on cycles appends unresolved nodes for one visit in model order; per-node exceptions do not stop later nodes. Its API reports cycle and failure details while `ok:true` can coexist with failed visitors. An atomic feature-rebuild proposal must explicitly adapt/review these behaviors, not assume they already reject cycles; remaining nodes in a topological remainder may include downstream nodes, not only cycle members. No runtime test.
- `analysis/analyze-tab.js`, `sheets`, `render`, `layers` and `io` are integration areas identified from the source tree, not audited capabilities. The historic gap note [2] describes older findings; verify against current main before claiming present/absent features.

## Failure cases, metrics and test design

Independent reference cases should supply explicit input, expected geometry and units, uncertainty, tolerances, source and version. Compare model geometry and topology first, then tessellation and screen image: endpoints/knots/weights, sampled and independent extremal deviations, area/volume only for valid solids, boundary identity and orientation, continuity along the full join, and render/projection error. Beware of sampling missing a local maximum; use analytic bounds or adaptive methods when required. Test cache invalidation, point selection, undo/redo transactions, copy/paste IDs, layer lock/visibility, save/reopen, imports/exports, offline asset availability, corrupt/oversized input, memory and cancel. Measure on supported devices; choose numeric thresholds before testing rather than treating the Python 1e-14 assertion as product acceptance.
