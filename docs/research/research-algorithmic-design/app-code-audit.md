# Algorithmic design: what the app already has

Audit of the app's own code, 2026-11-15, by a read-only research agent (level P: the code read as text; no
tests or builds run; `canvas_v10.html` not opened). The agent could not write files, so this is its condensed
hand-back as the coordinator received it; the longer per-heading audit stayed in the agent's transcript.
Paths are relative to `src/js/engine/`.

## 1. Dependency and rebuild machinery

- `bim/dependency-graph.js`: `bimGraphBuild` (85-136) derives the edges from the model on every call and never
  stores them. Edge kinds: level, type, host, source, region, link, tag, support, targetLevel (109-130).
- `bimGraphPropagate` (181-210) uses Kahn's ordering (154-176). A cycle is warned about and then visited in
  model order, not refused, and the result is still `ok:true`.
- The visitor is `bimGraphVisit` (`bim/region-dependents.js:255-327`); the entry point is
  `bimPropagateFrom(ids, 'rebuild'|'transform', delta)` (334-377).
- `saveSoon` (`bim/region-regenerate.js:96-110`) runs layer adoption, region regeneration (24-78) and a 300 ms
  save on every mutation.
- A type edit reaches its instances by a direct loop, not through the graph: `bimApplyTypeToInstances` /
  `bimRebuildInstanceForType` (`bim/type-instance-params.js:599-660`).

## 2. The queued pure-function files

Still header-only: `bim/parametric.js` (V204), `commands/flows.js` (V215), `site-tools/generators.js` (V213);
also `drawing/nurbs.js`, `bim/facade-openings.js`, `bim/cost-plan.js`. The specs and tests in
`docs/work-orders/v204`, `v213` and `v215` exist.

## 3. The element model

- Records sit in one flat array, `A3D.objs`, as `{id, t, name, pos, mesh:{v,f}, col, layer, bim:{type, ...}}`.
- Makers: `buildWallSolid` (`bim/import-compliance.js:179`), `buildFloorSolid`
  (`bim/ceiling-floor-profile.js:79`), `buildColumnSolid` (`bim/columns-openings.js:130`), `buildDoorOpening` /
  `buildWindowOpening` (406-437), `buildRoofSolid` (`bim/roofs.js:473`). Each calls `pushUndo` and repaints per
  element.
- Ids are `'a3d-'+Date.now().toString(36)+'-'+(A3D.seq++)`: stable across save and reopen, but re-running a
  generator gives new ids.
- There is no group or "generated by" field. The only precedent is `bimDgPlace`
  (`site-analysis/model-layers.js:59-104`), which keeps a stable key, the drawn output, and edited / orphan /
  gone states across re-runs.

## 4. Geometry

- CSG is a BSP in the style of csg.js (`bim/csg-booleans.js:45-201`); fragile when fed its own output and on
  many-way unions.
- Mesh primitives: `core/mesh-primitives.js`. Extrude: `padMesh`. Triangulation: `earClip`
  (`drawing/drawing-input.js:895-940`), with no holes.
- Zoning envelope: `bimZnCalc` (`site-analysis/zoning-envelope.js:251-321`), rebuilt only from zoning-record
  edits (`bimZnEdit`, 87-93).
- Arrays produce static copies (`editing/modify-toolbox.js:766`, `editing/precision-editing.js:325`).

## 5. Persistence and undo

- The saved record is an explicit field list (`core/objects-save.js:52`). The loader `bimApplyStoredState`
  (`core/state.js:64-131`) drops unknown top-level keys. `A3D.site.*` already carries zoning, tools and Ladybug
  data.
- Undo is a full JSON snapshot, 50 deep (`drawing/plan-mode-sketch.js:291-351`). A run of edits becomes one
  step with `setUndoSuspend` / `setBimUndoHold`.

## 6. History and branches

Commits store each element by id and hash (`history/element-history.js:37-46`); merge is three-way per element
and per field (`history/branches-merge.js:75-107`).

## 7. Workers

The only Blob-URL workers are Ladybug (`ladybug/runtime.js:154-201`, with transferables) and gzip
(`io/file-save.js:139-178`).

## 8. Rendering

No instancing. Meshes are batched into chunks by `bimSceneSync` (`render/gpu-batches.js:109-160`); a change is
detected by object identity: assign a new `o.mesh` object and call `paint()`.

## 9. UI patterns

- Panels are HTML strings with a `data-*` action dispatcher (`site-analysis/analysis-workspace.js:528`).
- The typed-parameter tools with run history (`site-tools/tools.js:196`) are the precedent for a rules panel.
- Commands: `a3drRegisterCommand` (`ui/discipline-tabs.js:134`); Properties fields: `bimPropLen`
  (`properties/palette.js:93`).
- The drawing canvas uses mouse and touch events; floating panels use pointer events.

## 10. Existing parametric objects

Primitives through `prm`; BIM types; linked clones; stairs and roofs as generators from parameters. Pad and
Pocket keep no feature record. Grids are snap points only.

## 11. Analyses a design loop could call

- `bimZnCalc` is synchronous.
- `bimLbRun` / `bimLbsRun` are asynchronous and one at a time; the code's own note gives about 3 s per 20,000
  faces for the ray step.
- `bimFrameSolve` and `bimUsageSummary` are synchronous.
- The cost plan is empty.

## Gaps

- No way to add many elements as one batch without the per-element UI side effects.
- No deterministic identity for generated elements, and no generated-by field.
- No stored graph or expression evaluator.
- Cycles are not refused before the live graph runs.
- Undo snapshots grow with every generated mesh.
- No instancing.
- No polygon boolean and no NURBS.
- No geometry worker.
- No optimisation loop.
- No node editor.
- No per-record schema migration.

## Hazards a generator must respect

- Undo: one `pushUndo`, then `setUndoSuspend` around the batch.
- Call `saveSoon` once, after the batch.
- Set `o.layer` explicitly, or layer adoption will place the element.
- Keep `seq` advancing when allocating ids.
- Wall rebuilds must go through `bimAfterWallRebuild`, or the openings are lost.
- Moving an element alone cuts its link to its source.
- Use `bimCarryBim` when rebuilding, so type and level survive.
- New top-level state must be added to the save, load, undo snapshot, undo restore and history lists, or it is
  lost; `A3D.site` avoids this.
- Replace `o.mesh` with a new object; editing it in place is not seen by the renderer.
- ES5 only; workers built from Blob URLs so `file://` keeps working.
