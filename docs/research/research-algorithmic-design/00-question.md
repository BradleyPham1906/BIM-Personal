# Algorithmic design: the question and the hypotheses

Written 2026-11-14, before any search (research-protocol.md, "The question first"). The main note is
`docs/research/research-algorithmic-design.md`; this file is kept as it was written so the outcome of each
hypothesis can be judged against what was claimed beforehand.

## The question

The owner (2026-11-14) wants the app to accommodate algorithmic design: building form, layout and elements
produced and rebuilt from explicit rules, parameters and relationships, not only drawn by hand. The owner
pasted a search engine's overview of the field (execution graphs, shape grammars, geometry kernels, IFC
mapping, optimisation, version control). That overview is a pointer, level U.

**How should BIM-Personal support algorithmic design inside its own contract (an ES5 engine, a one-file build
that runs offline from `file://`, vetted libraries pinned and loaded on demand, phone, tablet and desktop),
building on what is already queued (V204 feature records, V213 generators, V215 flows), and which algorithms
should it use?**

## What a good answer must decide

1. The execution model: a text program, a node graph, or both; one graph for the model or one per object;
   full or incremental re-evaluation.
2. How a generated thing becomes a BIM element and keeps its identity when the rules run again.
3. Which rule systems come first (split grammars for facades and massing, plan layout, others).
4. The geometry: the app's own meshes and CSG, or a kernel library (Manifold, OpenCascade), and when.
5. Where it runs: the main thread or a worker, given `file://`.
6. Optimisation: which method, with what evaluation budget, if any in the first phases.
7. The editor: our own node editor or a library; what works on a phone.
8. The order of phases, and how they sit with V204, V213 and V215.

## Hypotheses (each can be proved wrong)

- **H1, evaluation cost.** Re-evaluating a whole graph of 1,000 arithmetic nodes takes under one frame (16 ms)
  in plain ES5 here, so dirty-flag bookkeeping is not what makes a graph responsive; the geometry nodes are,
  and caching a node's output by its inputs is the saving that matters. (Measured here.)
- **H2, split grammar without a kernel.** A split grammar in the manner of CGA shape (split, repeat, component
  split, a scope) fits in under 400 lines of ES5 with no geometry kernel, and derives a 10-storey, 8-bay facade
  in under 50 ms. (Measured here.)
- **H3, identity.** An element generated by rules can carry a deterministic identity (its rule path and index)
  that survives a parameter change which keeps the counts, so data attached to it by hand survives; when the
  counts change the identity changes, and that must be reported, not hidden. Professional tools have met this
  same problem and their documents say how. (Literature and tools' documents; measured on the H2 prototype.)
- **H4, the kernel.** The app's own CSG is enough for the first slices (box and prism massing, facades, plates);
  a mesh-boolean library (Manifold) is needed only for booleans between arbitrary generated solids, and an exact
  B-rep kernel (OpenCascade) only for fillets, lofts and NURBS solids. (The app's code; the libraries' documents,
  licences and sizes. No upstream code is run without the owner's approval.)
- **H5, text or nodes.** Studies of algorithmic design in architecture find node graphs easier to start with and
  text programs better for large models. If so, a node graph with an expression node is the right first interface,
  and a text language is a later, separate decision. (Papers; the tools' own documents.)
- **H6, optimisation.** For the small evaluation budgets a browser allows (hundreds of runs, not tens of
  thousands), published benchmarks of architectural optimisation do not favour genetic algorithms; simpler direct
  search or model-based methods do as well or better. (Papers; a toy problem measured here.)
- **H7, the worker.** The pasted advice (SharedArrayBuffer, OPFS, a service worker) does not hold from `file://`:
  those need a secure or cross-origin-isolated context. A Blob-made classic worker with transferable buffers does
  work from `file://`, as the Ladybug runtime already shows. (Measured here in Chromium; MDN for the rest.)
- **H8, IFC.** If generators create the app's ordinary elements (walls, slabs, openings), IFC output needs nothing
  new beyond V177. (The app's code.)
